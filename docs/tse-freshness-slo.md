# TSE freshness: operational objective and publication contract

## Goal

Minimize the measured lag between availability of an official TSE JSON update
and availability of the corresponding public JSON on the site. **Exact same
instant is not guaranteed**: network, TSE polling, parsing, hosting and client
polling each add non-zero delay.

## Preserve incremental delivery

- Keep the existing live collector, conditional GETs and 137-target complete
  manifest. Only changed result JSONs are uploaded for each update; metadata
  (manifest, alerts, version) accompanies each delta.
- Do not copy all 137 JSON files on every 5-second publisher run. A full,
  immutable publication snapshot may be useful later, but it must not
  needlessly block fresh delta delivery.
- Continue to use HMAC-authenticated HTTPS. Validate metadata, paths, checksums
  and expected counts before exposing updates.
- Activation must be idempotent (repeat same batch is safe), monotonic
  (older generated_at cannot supersede newer), serialized per site, and must
  recover from interruption. Never run concurrent SSH and HTTPS writers.
- Stage first; use atomic replacement of each individual destination file.
  Promote version.json **last** after manifest and alerts. This is a
  per-file consistency barrier, NOT an atomic multi-file transaction.
  For strict browser-level cross-file consistency a reader protocol with
  immutable versioned paths and matching frontend changes is required.
- Never call collector commit() until the remote version has been durably
  activated and verified. Retried requests after a lost response must be
  idempotently reconcilable.

## Measure the real latency

Record **UTC timestamps** and source provenance per update:

1. `tse_payload_observed_at`: time a changed upstream response was received.
2. `collector_processed_at`: time processing completed.
3. `delta_upload_started_at` / `delta_upload_completed_at`.
4. `remote_activated_at`: time the remote server confirmed promotion.
5. `public_visible_at`: first independent HTTPS fetch observing the new
   version and expected changed result.

Useful metrics (milliseconds):

- detection-to-public = public_visible_at - tse_payload_observed_at
- processing = collector_processed_at - tse_payload_observed_at
- transfer = delta_upload_completed_at - delta_upload_started_at
- activation = remote_activated_at - delta_upload_completed_at

`generated_at` is generated by our pipeline, **not** proof of TSE's
original publication time. Do not label it as TSE publication latency.
To measure true TSE-to-site delay, obtain trustworthy upstream publication
timestamps where available and compare against synchronized clocks.

## Observed cadence is not end-to-end latency

The current live-publisher timer runs at 5-second intervals and the browser
checks version.json at about 5-second intervals; upstream polling cadence and
remote activation overhead must also be accounted for. Never promise a 5-second
TSE-to-site SLA based on either timer alone.

## Production gates

- Test staged real-shaped deltas with fault injection for 409 replay, 413
  oversized upload, 422 checksum mismatch, 5xx, broken network and retries.
- Enforce bounded batch retention/quota and prevent orphan staging growth.
- Verify PHP web/CLI runtime restrictions and the host's handling of
  concurrent file operations. Measure p50/p95/p99 lag during election updates.
- Rollout only with a reversible maintenance plan; keep the SSH implementation
  available as rollback and leave production timer unchanged until validated.
